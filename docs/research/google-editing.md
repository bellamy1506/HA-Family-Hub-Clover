# Editing Jenn's Google events from the board

Research note, 2026-11-01, for fork issue [#100](https://github.com/bellamy1506/HA-Family-Hub-Clover/issues/100) (map [#37](https://github.com/bellamy1506/HA-Family-Hub-Clover/issues/37)), the Google counterpart of [#39](https://github.com/bellamy1506/HA-Family-Hub-Clover/issues/39) ([icloud-editing.md](https://github.com/bellamy1506/HA-Family-Hub-Clover/blob/research/icloud-editing/docs/research/icloud-editing.md)). Question: Home Assistant's Google Calendar integration, set up read-write, can add and delete events but not change them. Can Family Hub's backend change Jenn's Google events itself (title, day, time, place, details, Delete, "This one / All") with the integration's own sign-in, and can the Whose row (owner, [#98](https://github.com/bellamy1506/HA-Family-Hub-Clover/issues/98#issuecomment-6559117623) decision 9) move an event between Will's iCloud, Us and Jenn's Google without changing its `uid`? What does Google do on its own, what breaks, and what does it cost to own?

**Addendum, same day:** two requirements from the owner's [#104 decisions 1 and 8](https://github.com/bellamy1506/HA-Family-Hub-Clover/issues/104#issuecomment-6564600586) ([requirements comment](https://github.com/bellamy1506/HA-Family-Hub-Clover/issues/100#issuecomment-6564602300)): the Repeats row (section 3a) and shared plans between Will and Jenn changing as one (section 3b), which replaces the first version's "refuse every event with guests". Sections 4 to 10, the lab and the supervised check are extended to match.

Lines marked **[inference]** are my own judgement, not something a source states. Sources: Home Assistant 2026.10.4's own source, from its PyPI wheel (uploaded 2026-10-24): `homeassistant/components/google/`, `components/calendar/`, `helpers/config_entry_oauth2_flow.py`; `gcal_sync` 9.2.0 (Home Assistant 2026.10.4's pin, PyPI 2026-09-19, also the latest release and still the `dev` branch's pin on 2026-11-01); Google's Calendar API reference and guides (each page's "last updated" date given), the API's discovery document (revision 20261028, fetched 2026-11-01); Google's OAuth pages; Home Assistant's Google Calendar page (fetched 2026-11-01); Family Hub on `house/board-next` at `770d617`. Nothing touched the house, a real Google account or a real iCloud account: the lab below ran against an in-memory stand-in for Google and a local Radicale, with made-up events.

## The answer

**Yes.** Google's Calendar API changes any event in place (`events.patch`), one occurrence of a repeating one included, and refuses a stale write when told the version it last read (`If-Match`). Home Assistant's Google integration already holds Jenn's sign-in with the full calendar scope; Family Hub can borrow it through Home Assistant's own public OAuth helper, so nothing new appears on Jenn's consent screen and no second sign-in is stored. Home Assistant's `recurrence_id` for a Google occurrence is Google's own instance id, so finding the right event needs no time search (unlike iCloud). The Whose row can keep the `uid` both ways: Google takes a caller's `iCalUID` on a new event, and CalDAV takes any UID; the order is "write the new copy, check it, then delete the old", so a failure leaves exactly one copy. Three things shape the build: Home Assistant reads Google from a local copy refreshed every 15 minutes, so every write must refresh it; Home Assistant's own Google delete can remove the wrong occurrence in one case (lab check L), so the house path should do Google deletes too; and a few Google behaviours aren't documented and need the supervised check. Repeats are a patch of the event's `recurrence`: a one-off keeps its id and iCalUID when it starts repeating, and "Never" ends the series with an inclusive `UNTIL` at the opened occurrence (section 3a). A plan Jenn organized whose only other guest is Will is changed on her copy with `sendUpdates=all`, the one write that mails anyone, because Google's update email is the only thing that reaches Will's iCloud copy; whether iCloud applies that email by itself isn't documented by Apple and decides #104's fallback (section 3b). About 150 lines for edit and delete, 60 for repeats, 15 for shared plans, 130 for the Whose conversion, 40 of wiring and 300 of tests; it fails safe, back to today's add-and-delete, if Home Assistant changes what it relies on.

## 1. What's already built or decided

- **Home Assistant's Google entity declares add and delete only:** `self._attr_supported_features = CalendarEntityFeature.CREATE_EVENT | CalendarEntityFeature.DELETE_EVENT`, set only when the entity isn't read-only (`google/calendar.py`, `GoogleCalendarEntity.__init__`), and read-only means the calendar's role isn't writer or the entry's access isn't `read_write` (`_get_entity_descriptions`). Home Assistant's `dev` branch is the same on 2026-11-01 (`google/calendar.py` line 343).
- **What the entity reports for each event** (`_get_calendar_event`): `uid=event.ical_uuid` and `recurrence_id=event.id if event.recurring_event_id else None`. For a Google-made event the iCalUID is `<id>@google.com` (lab R1). The calendar's id is on the entity as `calendar_id`.
- **Reads come from a local copy, not from Google:** each entity's coordinator runs `gcal_sync`'s `CalendarEventSyncManager` (an incremental sync with a sync token) every 15 minutes (`google/coordinator.py`, `MIN_TIME_BETWEEN_UPDATES`), and `async_get_events` answers from that copy's timeline (`CalendarSyncUpdateCoordinator.async_get_events`). Home Assistant's own create and delete call `await self.coordinator.async_refresh()` afterwards (`async_create_event`, `async_delete_event`).
- **The default access is read-write:** `DEFAULT_FEATURE_ACCESS = FeatureAccess.read_write`, scope `https://www.googleapis.com/auth/calendar`; read-only is `calendar.readonly` (`google/const.py`). A new entry is created with `calendar_access: read_write` (`config_flow.py`, `async_oauth_create_entry`).
- **Family Hub's commands** (`custom_components/family_hub/__init__.py` on `house/board-next`): `delete_support` reports the entity's bits, `delete_event` and `update_event` call the entity's `async_delete_event`/`async_update_event` only when the bit is set, and fields arrive through `_build_entity_event_fields` as `dtstart`/`dtend`. The iCloud note adds a house path inside these commands for CalDAV; this one adds Google beside it.
- **Decided:** Jenn's Google read-write with her okay (#98 decision 8); the Whose row, Will · Jenn · Us, a repeating event moves as a whole, with Undo (decision 9); Jenn's Google connects before slice 1 with the Cloud project published ([switch-over.md](https://github.com/bellamy1506/HA-Family-Hub-Clover/blob/house/board-next/docs/board-next/switch-over.md), "Before slice 1"); Us moves to iCloud with the event sheet (same file); never change an event by replacing it with a new UID (A19, [gaps.md](https://github.com/bellamy1506/HA-Family-Hub-Clover/blob/house/board-next/docs/research/calendar-card-pro/gaps.md)); re-ask after a save (A12, same file); "This one / All" only, no "this and following" (gaps.md row 69). Added the same day by #104: a shared plan on two calendars changes and deletes as one, invitations between Will and Jenn become changeable, invitations from anyone else stay refused, the echo names any copy the board couldn't change, Whose doesn't move a shared plan (decision 1); a Repeats row (Never, Every week, Every 2 weeks, Every month on the same date, Every year), "Never" on a repeating event ending it after this one with earlier ones kept and Undo restoring it, and Clover's "every Tuesday … until June" (decision 8 and its calls).

## 2. The sign-in: reuse it, change nothing Jenn sees

- **How Home Assistant holds it.** The entry stores the token (access token, refresh token, `expires_at`, `scope`) in `entry.data["token"]`. `config_entry_oauth2_flow.OAuth2Session(hass, entry, implementation)` refreshes it when needed (`async_ensure_token_valid`, under a lock, writing the new token back to the entry) and `async_request(method, url, **kwargs)` sends a request with the bearer token and any extra headers; the implementation comes from `async_get_config_entry_implementation(hass, entry)` (`helpers/config_entry_oauth2_flow.py`). A refresh merges the new token over the old one (`{**token, **new_token}`), keeping the refresh token (`LocalOAuth2Implementation._async_refresh_token`).
- **Family Hub's way in:** find the Google entity's config entry, build its own `OAuth2Session` from it with that public helper, and call `https://www.googleapis.com/calendar/v3/...` with `async_request`. Every integration that uses OAuth2 in Home Assistant uses this helper, so it is the stable surface **[inference]**. Two sessions on one entry each have their own lock and may both refresh at once; each gets a valid access token and the refresh token survives the merge, so that race is harmless **[inference]**.
- **Why not `gcal_sync` itself.** `entry.runtime_data.service` is the integration's `GoogleCalendarService`, but its token source is private (`_auth`), and its request helper can't carry an `If-Match` header: `AbstractAuth.request` passes `**kwargs, headers=headers`, so a caller's own `headers` raises a `TypeError` (`gcal_sync/auth.py`). Its `async_patch_event(calendar_id, event_id, body)` takes a raw body but no version check and no `sendUpdates`; it has no import, insert-with-iCalUID or move call; its `Event` model keeps neither `etag` nor `organizer` (`gcal_sync/api.py`, `model.py`, `EVENT_FIELDS`). So the house path calls the API directly and uses `gcal_sync` only through Home Assistant's reads.
- **Scope:** `events.patch`, `events.delete`, `events.insert`, `events.import` and `events.instances` all accept `https://www.googleapis.com/auth/calendar` ([discovery document](https://www.googleapis.com/discovery/v1/apis/calendar/v3/rest), rev 20261028). Read-write is already what Home Assistant asks for (`config_flow.py`, `extra_authorize_data`: that scope, `access_type: offline`, `prompt: consent`). The write path needs no wider grant.
- **What Jenn's consent screen shows:** Google words that scope as "See, edit, share, and permanently delete all the calendars you can access using Google Calendar" ([Choose Google Calendar API scopes](https://developers.google.com/workspace/calendar/api/auth), updated 2026-09-03). That is the switch-over's step 4 as approved; the write path adds nothing to it.
- **The Google Cloud setup, and the 7 days.** Google: a project with external user type in "Testing" publishing status "is issued a refresh token expiring in 7 days", and an account holds at most 100 refresh tokens per client, the oldest invalidated "without warning" ([Using OAuth 2.0](https://developers.google.com/identity/protocols/oauth2), "Refresh token expiration", updated 2026-10-29). Home Assistant's page: Audience External, **Publish app**, "Otherwise, your credentials will expire every 7 days", a "Web application" client with the redirect URI `https://my.home-assistant.io/redirect/oauth`, and "you may get a message telling you that the app has not been verified and you will need to acknowledge that in order to proceed" ([Google Calendar integration](https://www.home-assistant.io/integrations/google/), fetched 2026-11-01). An unverified published app shows an "unverified app" screen before the consent screen and is "limited to 100 new users until it is verified" ([Unverified apps](https://support.google.com/cloud/answer/7454865), fetched 2026-11-01). The switch-over already has all of this; nothing changes for the write path.
- **When the sign-in fails** (revoked, unused six months, Google's 100-token rule), `OAuth2Session` raises and starts Home Assistant's re-authentication (`async_ensure_token_valid`, `async_start_reauth_if_available`). The board then says it couldn't change the event **[inference]**; reads stop for the same reason, so the board's stale-calendar line covers it.

## 3. Finding the right event, and changing it

- **One-off:** `events.list?iCalUID=<uid>` ("Use this if you want to search for an event by its iCalendar ID", discovery document) returns the event with its `etag`, `organizer` and `attendees`. A live lookup, never Home Assistant's local copy (see L below).
- **An occurrence:** Home Assistant's `recurrence_id` is `<series id>_<original start>`, in UTC (`20261103T230000Z`) or a date for all-day (`20261111`) (`gcal_sync/model.py`, `SyntheticEventId.event_id`; lab R2, R3, across the 1 Nov clock change). The house path splits it into the series id and the original start and asks `events.instances?originalStart=...` ("The original start time of the instance in the result", [instances](https://developers.google.com/workspace/calendar/api/v3/reference/events/instances), updated 2026-07-29), which returns that occurrence with its own id and etag, whether it was already changed or not. Google: `originalStartTime` "uniquely identifies the instance within the recurring event series even if the instance was moved to a different time" ([Events resource](https://developers.google.com/workspace/calendar/api/v3/reference/events), updated 2026-07-07). So a moved occurrence keeps its `recurrence_id` (lab B), and the board needn't send where it shows now.
- **Change one occurrence ("This one"):** `PATCH` the instance with only the changed fields. Patch semantics: "Fields that you don't specify in the request remain unchanged", and arrays sent replace the old ones ([patch](https://developers.google.com/workspace/calendar/api/v3/reference/events/patch), updated 2026-07-01). Google makes it an exception of the series ([Recurring events](https://developers.google.com/workspace/calendar/api/guides/recurringevents), updated 2026-09-17, which uses `update`; patch on the instance is what `gcal_sync` already does for deletes). The uid and recurrence_id don't change (lab A).
- **Delete one occurrence:** `PATCH` the instance to `"status": "cancelled"`, as `gcal_sync` does (`api.py`, `CalendarEventStoreService.async_delete_event`) and as Google's guide shows. Undo patches it back to `confirmed` (lab C2; on real Google, supervised check step 5).
- **Change all:** patch the series. For text (title, place, details) the house path also patches each live exception, so "All" means all whatever Google does with exceptions (lab E2; whether Google carries it over itself is step 6). For a new time or day it moves the series by however far the opened occurrence moved, and a weekly rule's `BYDAY` moves with the day (lab E3). **If the series has exceptions (moved or deleted occurrences), a time or day change for all is refused** with "change the time of all in Google Calendar": Google doesn't say what happens to exceptions keyed to the old times, and a deleted Tuesday coming back would be a visible fault **[inference]**. Step 7 tells whether this can be lifted.
- **Delete all, or a one-off:** `DELETE` the series or event. Google keeps it as a tombstone: "On the organizer's calendar, cancelled events continue to expose event details (summary, location, etc.) so that they can be restored (undeleted)", and "such cancelled events will eventually disappear" (discovery document, `Event.status`). So Undo restores the same event, same id and same uid, by patching `status` back to `confirmed` (lab G), and re-confirms any exception the delete took.
- **All-day and timed:** a timed change sends `{"dateTime", "timeZone"}` with the event's own time zone (Google: for repeating events `timeZone` "is required and specifies the time zone in which the recurrence is expanded", Events resource); all-day sends `{"date"}` with Google's exclusive end date (which Home Assistant's `dtend` already is). Switching between the two also sends the other key as `null` **[inference: untested on Google; rare]**.
- **Version check:** "you can specify an `If-Match` header that contains the value of the etag from the previous retrieval. Otherwise, you will get a 412 (Precondition failed) response code", with "no support for conditional modifications for insert operations" ([Version resources](https://developers.google.com/workspace/calendar/api/guides/version-resources), updated 2026-09-11). Every patch and delete carries the etag just read (lab H); Undo carries the etag its own write produced, so an Undo after someone changed the event again is refused rather than winning (lab K).
- **Refuse what Jenn didn't make herself**, as the iCloud path refuses invitations: an event is changeable only if `organizer.self` is true ("Whether the organizer corresponds to the calendar on which this copy of the event appears"), no attendee other than herself is listed (except Will, section 3b), it isn't `locked`, and its `eventType` is `default` (birthdays, out-of-office, focus time, working location and from-Gmail events can't be moved and are special, [move](https://developers.google.com/workspace/calendar/api/v3/reference/events/move), updated 2026-05-12). Events Jenn organized with anyone but Will as a guest are refused too: a change would otherwise notify them or leave their copies stale (section 5). Lab I. `guestsCanModify` ("Whether attendees other than the organizer can modify the event", default false) doesn't matter: the board writes only copies Jenn organized.
- **A repeating event with no occurrence and no "All"** is refused (lab J), as on iCloud.

## 3a. Repeats (#104 decision 8)

- **Already there:** Home Assistant's Google create passes a rule as `event.recurrence = [f"RRULE:{rrule}"]` (`google/calendar.py`, `GoogleCalendarEntity.async_create_event`, lines 487 and 488 in 2026.10.4; #104 cites 464 and 465, likely another version), after the calendar component checks it with `validate_rrule` (it must parse with `dateutil` and have a FREQ: `calendar/helper.py`). So a new repeating event, Clover's "every Tuesday until June" included, needs no house path; the Repeats row on an existing event does.
- **The rules:** Every week `FREQ=WEEKLY`, Every 2 weeks `FREQ=WEEKLY;INTERVAL=2`, Every month `FREQ=MONTHLY` (the same date, taken from the start), Every year `FREQ=YEARLY`. "Until June" adds `UNTIL`, which bounds the rule "in an inclusive manner" and, for a start with a time zone, "MUST be specified as a date with UTC time" (RFC 5545 section 3.3.10); the path writes the end of that local day in UTC, or a plain date for all-day. Google's own example has the same shape, `RRULE:FREQ=WEEKLY;UNTIL=20110701T170000Z` with a named `timeZone` on start and end ([Recurring events](https://developers.google.com/workspace/calendar/api/guides/recurringevents), updated 2026-09-17). Every month on the 29th to 31st skips months without that date: "Recurrence rules may generate recurrence instances with an invalid date … Such recurrence instances MUST be ignored" (RFC 5545 section 3.3.10; lab RP8 shows `dateutil`'s reading, Google's is step 17).
- **One-off to repeating:** `PATCH` the event with `recurrence: ["RRULE:…"]`, plus a named `timeZone` on start and end if missing ("For recurring events this field is required", Events resource). The event keeps its `id`, so its iCalUID and the board's `uid` stay; its occurrences get recurrence_ids `<id>_<start>` (lab RP1). Google doesn't document turning a single event into a series by patch; the patch semantics allow it and step 14 confirms it **[inference]**. Undo patches `recurrence: []` back (RP2; step 14 checks Google accepts an empty list).
- **"Never" on a repeating event:** end the series after the opened occurrence, earlier ones kept: drop `COUNT` and set `UNTIL` to that occurrence's original start (inclusive, so it is the last), in UTC. This is what `gcal_sync` already does for "this and following" deletes (`UNTIL` one day before, `count = None`: `api.py`, `async_delete_event`), and it keeps one series under one uid; splitting into two series isn't needed because nothing continues **[inference]**. Changed occurrences after the cut-off: Google doesn't say whether it drops them, so the path cancels each one first, explicitly (lab RP4). Undo puts the old `recurrence` back first, then restores those occurrences (RP5).
- **Changing the rule** (Every week to Every 2 weeks): replace the `RRULE` line, keeping its `UNTIL` or `COUNT` unless a new end was said (RP6, Undo RP7). On a series with changed or deleted occurrences it is refused, "change the repeat in Google Calendar", for the same reason as a time change for All (RP3): Google doesn't say what happens to exceptions the new rule no longer produces. Step 16 tells whether this can be lifted.
- **Reading the current rule:** Home Assistant reports `rrule` only when Google's `recurrence` is a single `RRULE:` line, and reports none on a changed occurrence (`_get_calendar_event`; lab O4). So the Repeats row reads the rule from any unchanged occurrence of the series, and a move from iCloud writes `EXDATE`s as cancelled occurrences (as Google itself keeps deleted ones), never as `EXDATE` lines that would blank the rule (O4).
- **iCloud's side, briefly** (#104 adds it to #39's check): the same three cases on the calendar object with `icalendar`: add an `RRULE`; for Never set `UNTIL` in UTC, drop `COUNT` and the `RECURRENCE-ID` components after the cut-off; refuse a new rule when the object has exceptions or `EXDATE`s; save with `If-Match`; Undo saves the old text back (lab RC1 to RC3 against Radicale).

## 3b. Shared plans between Jenn and Will (#104 decision 1)

- **What counts as one:** Jenn's copy has `organizer.self` true, `attendeesOmitted` isn't set, and every attendee other than Jenn herself (`self` true) has an email in Will's addresses, compared without case, and isn't a `resource` (Events resource: `attendees[].self`, `.resource`, `.email`; `attendeesOmitted`). Will's addresses come from Family Hub's settings (his iCloud calendar address, and any other he uses), never from the repo. Anyone else as a guest, a room or resource, or Jenn as a mere guest of someone's invitation (`organizer.self` false) is refused as before (lab SH6).
- **Jenn as a guest of Will's iCloud invitation:** refused on the Google side; the board changes Will's copy, the organizer's, through the iCloud path, and Apple's update reaches Jenn's Gmail (#104 decision 1). What happens if an attendee's Google copy is patched isn't documented (changed locally, refused, or sent nowhere); the board never tries **[inference]**.
- **Which `sendUpdates`:** with `none`, Google's help says guests' calendars still update for Google Calendar users, but "Non-Google Calendar users and Google Calendar users with a non-Gmail email provider get an email, which updates their calendar per the settings of their calendar service" only when emails are sent ([Invite people to your Calendar event](https://support.google.com/calendar/answer/37161?hl=en), fetched 2026-11-01). Will's iCloud address is a non-Google guest, so `none` would leave his copy stale. `externalOnly` ("Notifications are sent to non-Google Calendar guests only") and `all` send him the same email when he is the only guest; the path uses `all`, Google Calendar's own "Send", so it still works if Will's address on a plan is a Google account **[inference]**. Shared-plan writes (change, delete, Undo) are the only ones that say `all`; every other write stays `none` (lab T, T2).
- **What Will sees:** an email from Google with the updated invitation (Google's help above). On his side Apple offers, per address, "Event invitations appear as notifications in Calendar on iCloud.com" or "Event invitations are emailed to the address specified" ([iCloud User Guide, receive invitations](https://support.apple.com/en-gb/guide/icloud/mm6b1a8534/icloud), no date, fetched 2026-11-01). Whether iCloud applies an emailed update from Google to an invitation Will already accepted, without him acting, is **not documented by Apple**. Reports disagree: updates from outside organizers "appear in my calendar on my iPhone, but not in same calendar on my macs" (Apple Community, 2024-06-04), and "Apple Calendar does not recognize updates made to calendar invites authored by and sent by others to me" (2023-06-21, [thread](https://discussions.apple.com/thread/254943312)). Under iTIP the update carries the same UID and a higher SEQUENCE (RFC 5546), and Google's `sequence` rises on each change (lab SH2) **[inference that Google's email follows it]**. Step 19 settles it. **If Will has to accept each update by hand, that is the case #104 already decided: invitations fall back to option C, no change, only Hide.**
- **Delete:** `events.delete` with `sendUpdates=all` ("Guests who should receive notifications about the deletion of the event", [delete](https://developers.google.com/workspace/calendar/api/v3/reference/events/delete)) sends Will a cancellation (lab SH3; iTIP's `CANCEL`, RFC 5546 **[inference]**). Undo restores Jenn's copy and sends again (SH4); whether Will's iCloud copy comes back, or he must accept again, is step 20.
- **The two copies are one plan by uid:** iTIP keeps the event's UID across organizer and attendees (RFC 5546), so Will's iCloud copy carries Jenn's iCalUID **[inference until step 18]**. The board already treats the same uid and start as one plan. After a write it re-asks both calendars (A12); if Will's copy still shows the old time, the echo names it ("Moved on Jenn's calendar. Will's copy is still at 7:00", #104's own example), and the line clears when his copy catches up **[inference: email can take longer than the 10 s window]**. The board writes only Jenn's copy for a plan she organized: an attendee's CalDAV copy changed directly would be Will's alone and overwritten by the next update **[inference]**.
- **Whose doesn't move a shared plan** (decision 1): the path refuses it (lab SH5).
- **Undo** is one step: the board's own etag makes an older Undo lose (lab K), so each Undo mails Will once more.

## 4. The Whose row: moving between iCloud and Google

- **Identity can be kept both ways.** The board keys on `uid`, which is Google's `iCalUID` and CalDAV's `UID` (section 1; [marks-over-time.md](https://github.com/bellamy1506/HA-Family-Hub-Clover/blob/research/marks-over-time/docs/research/marks-over-time.md), line 50). Google: the iCalUID "is used to uniquely identify events accross [sic] calendaring systems", must be supplied to `events.import`, and "only one of [id or iCalUID] should be supplied at event creation time" (discovery document, `Event.iCalUID`), so a new Google event can carry the iCloud UID. CalDAV stores whatever UID the object holds (RFC 4791 section 4.1), so an iCloud copy can carry `…@google.com`.
- **Jenn to Will or Us (Google to CalDAV):** read the series, its exceptions and its cancelled occurrences (`events.list?iCalUID=…&showDeleted=true`); write one calendar object: the series with its `RRULE`/`EXDATE`/`RDATE` lines copied from Google's `recurrence` ("List of RRULE, EXRULE, RDATE and EXDATE lines … as specified in RFC5545", Events resource), each cancelled occurrence as an `EXDATE`, each changed one as a `RECURRENCE-ID` component, popup reminders as alarms; save it to the iCloud calendar; read it back and compare the occurrences in the board's window with Google's; only then delete Google's copy. Lab M: same occurrences (the moved one moved, the deleted one deleted), same uid, alarm kept, one copy.
- **Will or Us to Jenn (CalDAV to Google):** convert the object the same way back (alarms to popup reminders, `EXDATE`s into `recurrence`), create it on Jenn's calendar with the same iCalUID, patch each changed occurrence onto its instance, compare, then delete the CalDAV object. If Google already holds a tombstone for that uid (the event was Jenn's before), restore it rather than create a second one (lab Q). Lab O: Apple's UID kept, exception and `EXDATE` kept, the 10-minute alarm a popup reminder.
- **Order and failure.** New copy first, check, then delete the old. If writing or checking the new copy fails, it is removed and the old one stays; if deleting the old one fails (412, or offline), the new copy is removed (lab S1, S2). If that removal also fails, both copies exist with one uid; the board already treats the same `uid` and start as one plan (marks-over-time.md, implication 6), so nothing shows twice **[inference]**, and Family Hub retries the clean-up.
- **What doesn't travel:** Google colors, call links and attachments have no iCloud home, so an event with a call link or files is refused ("move it in Google Calendar"); Apple's private `X-APPLE-` fields don't reach Google (Undo restores them, lab P). An event with Google's default reminders (`useDefault`) gets the iPhone's default alerts on iCloud, and the reverse **[inference]**. Moves to Google are written as busy (`transparency: opaque`), because Home Assistant hides Google events marked free unless set otherwise (`_event_filter`, `ignore_availability` false for calendars set up in the UI), and a moved event must not vanish from the board.
- **Undo** restores the old side first, then removes the new: Google's tombstone is restored (same id, uid, exceptions; lab N), or the CalDAV object's own text, kept from before the move, is saved back (alarms, notes and Apple fields included; lab P).
- **Where identity can't be kept:** if the supervised check shows Google rewrites a caller's iCalUID or refuses one (step 11), or if Us were still a Local Calendar (Home Assistant's Local Calendar takes no uid on create and `ical` makes a new one: `local_calendar/calendar.py`, `async_create_event`; `ical` 14.3.0, `Event.uid`'s default factory). Then Family Hub moves the event under a new uid and, in the same command, rewrites its own records (Hide, first-seen, settled clashes) from the old uid to the new one, so the board shows a move, not a new event. For that to work in every case the board's records should key on `uid` alone, not on calendar plus uid **[inference]**. Us moving to iCloud with the event sheet (switch-over) means the Whose row ships with both iCloud sides able to keep UIDs.
- **Not for shared plans:** a plan between Jenn and Will shows both names and stays where it is (section 3b).
- **Not on the row:** moving between two of Jenn's own Google calendars (`events.move`, "changes an event's organizer") isn't a Whose change; Will to Us is iCloud to iCloud, the same write-check-delete with the object text unchanged, and belongs to #39's build and its supervised check.

## 5. What Google does on its own

- **`sendUpdates`:** patch, delete and move take `all`, `externalOnly` or `none`; the reference states no default, and the deprecated `sendNotifications` defaults to false with "some emails might still be sent even if you set the value to false" ([patch](https://developers.google.com/workspace/calendar/api/v3/reference/events/patch), [delete](https://developers.google.com/workspace/calendar/api/v3/reference/events/delete), updated 2026-05-12). The house path sends `sendUpdates=none` on every write except a shared plan's, which sends `all` (section 3b; lab T, T2), and refuses every other event with guests, so nobody else is mailed. For inserts Google warns that `none` "can have significant adverse effects, including events not syncing to external calendars or events being lost altogether for some users" (discovery document, `insert`); with no guests it has nobody to affect **[inference]**.
- **Jenn:** the change is made with her own sign-in, so Google treats it as her own edit; nothing found says Google notifies a calendar's owner of her own changes **[inference]**; step 13 watches for it. Her phone shows the change at its next sync.
- **Edit history:** an event's `updated` time and `sequence` change; Google keeps no per-event history a personal account can open, and a deleted event stays restorable only for a while (section 3) **[inference for the history part]**.
- **Quota:** "each patch request consumes three quota units" (patch page). A household's edits are far inside a project's daily allowance **[inference]**.
- **Avoid:** writing without `If-Match`, writing with `sendUpdates` left out, editing an event with any guest but Will, editing a copy Jenn didn't organize, and changing a series' time or rule when it has exceptions (until steps 7 and 16 say otherwise).

56 of 56 checks passed (35 in the first version, 21 added for #104). What the lab taught:

1. **Home Assistant's own Google delete can remove the wrong occurrence.** `gcal_sync`'s `async_delete_event` finds the event by iCalUID in the local copy and takes the first match (`_lookup_ical_uuid`). Google gives a changed occurrence the series' iCalUID (Events resource, `iCalUID`), so if the copy lists the exception first, "delete this occurrence" deletes the exception's id instead, and "delete all" deletes only that exception. Google promises no order; whether it ever lists an exception first is unknown, and a tombstone sharing the iCalUID would mislead it the same way **[inference]**. The house path looks up live by iCalUID and series id, so it should do Google deletes too, not call the entity's.
2. **Home Assistant's reads lag writes until its copy is refreshed.** The board's re-ask would show the old event until the coordinator syncs; Family Hub must call `entity.coordinator.async_refresh()` after each write, as Home Assistant's create and delete do.
3. **An out-of-date Undo must lose.** Keeping the etag from the board's own write makes Undo refuse once the event has changed again (K).
4. **A changed occurrence copied to iCloud needs the series' alarm and fields**, so the exception is built from the series plus the occurrence's changes; a cancelled occurrence becomes an `EXDATE`.
5. **`icalendar`'s `add_missing_timezones()` writes a VTIMEZONE valid only "from 1970-01-01 to 2038-01-01"** (its own comment line). Fine for the house; noted.
6. **Home Assistant's `rrule` is fragile:** it is reported only for a single `RRULE:` line and never on a changed occurrence (O4), so the Repeats row reads the rule from an unchanged occurrence, and the board never writes `EXDATE` lines to Google.
7. **"Never" needs the changed occurrences after the cut-off removed explicitly,** or what Google does with them decides (RP4); Undo must restore the rule before them.

Not tested: Google itself, or iCloud's handling of Google's update email (`fake_google.py`'s `mail` only records what Google's help says is sent). `fake_google.py` copies Google's documented behaviour and assumes the rest; the supervised check covers each assumption.

## 7. Staying in step

- **Home Assistant's Google entity:** after each write, `await entity.coordinator.async_refresh()` (one incremental sync, a single API call when nothing else changed **[inference]**), then answer the board; its re-ask (A12) then sees the change. Changes made on Jenn's phone still reach the board within 15 minutes, as today.
- **The server's calendar copy:** refresh that calendar's window after a write, as the iCloud note does.
- **Whose moves** refresh both entities and both calendars' copies.
- **Undo** holds the old fields (edits), the tombstone's id (deletes), or the old object text (moves).

## 8. The options

| | Option | Confidence it's the right way |
|---|---|---|
| A | A house write path in Family Hub for Google: its `update_event` and `delete_event` commands, for a Google calendar, call the Calendar API directly with Home Assistant's own sign-in (`OAuth2Session` from the entry), If-Match and `sendUpdates=none`; the Whose row moves events with the same uid | 0.72 |
| B | Patch Home Assistant's Google entities while running, adding `UPDATE_EVENT` and `async_update_event` | 0.06 |
| C | Contribute update to Home Assistant's Google integration and `gcal_sync`, and wait | 0.10 |
| D | A separate custom integration with its own Google sign-in | 0.04 |
| E | Keep Google to add and delete; change Jenn's events on her phone | 0.08 |

B changes a core integration's objects from outside and has to redo it on every reload; a quiet failure looks like a working button that does nothing, the iCloud note's reason too. C is the best long-term floor and A's module could be offered upstream, with the delete fault (lesson 1) reported, but it isn't in the house's hands. D gives Jenn a second consent screen and a second stored token for no gain. E costs nothing and leaves her typos and moved plans unfixable from the board, against decisions 8 and 9.

## 9. What could break

- **Home Assistant internals the path relies on:** the entity's `calendar_id`, its coordinator's `config_entry` and `async_refresh()`, the entry's `token` and `calendar_access` option, and the `recurrence_id` form. Each is checked before use; if one is missing, `delete_support` reports no update for Google, and the board keeps Home Assistant's own add and delete and says "change it in Google Calendar".
- **`gcal_sync` changes** affect only Home Assistant's reads (the recurrence_id form); the lab's R checks pin it.
- **Google's undocumented behaviour** (instance ids, what happens to exceptions on a series change, insert with an iCalUID, restoring a tombstone): the supervised check before building; anything that fails there is refused with "change it in Google Calendar", never guessed.
- **The sign-in lapses:** Home Assistant asks for re-authentication; reads and writes both stop; the board's stale-calendar line shows it.
- **Races with Jenn's phone:** 412, the board says it changed a moment ago and re-reads.
- **Will's addresses in Family Hub's settings:** if a plan uses an address that isn't listed, it is refused as an invitation, the safe side.
- **iCloud doesn't apply Google's update email by itself** (step 19): #104's fallback, invitations go to "no change, only Hide".
- **Rare cases, a note and no more:** switching an event between all-day and timed; an RRULE with `BYDAY` and a numbered weekday (refused for a day change); a series whose master isn't on Jenn's calendar; two copies left by a failed clean-up (shown as one).

Lock-in check: none. It's Google's public Calendar API through the sign-in Home Assistant already has; no new app, account or subscription; removing the code returns Google to add and delete.

## 10. What it costs to own

- **Code:** `google_write.py` of about 150 lines (find, check, update, delete, Undo; no Home Assistant imports, tested on its own like `calendar_cache.py`), the Whose conversion of about 130 lines (shared with the iCloud path, which already parses calendar objects with `icalendar`), about 60 lines for the Repeats row on Google and 40 on iCloud, about 15 for shared plans (the attendee rule and `sendUpdates=all`), about 40 lines of wiring in the commands (route Google entities to it, build the session, refresh afterwards; `delete_support` reports update for Google), and about 300 lines of tests that reuse `fake_google.py` as a fixture. No new dependency: aiohttp ships with Home Assistant, and `icalendar` is already the iCloud path's.
- **Watching:** read the notes of any Home Assistant release that touches `components/google` or bumps `gcal-sync`.
- **One-time:** the supervised check below.

## Recommendation

**Build option A, in the same wave as the iCloud path.** The smallest robust shape:

1. Borrow Home Assistant's sign-in: `OAuth2Session` from the Google entity's entry, through `async_get_config_entry_implementation`; never store a token of Family Hub's own.
2. Find the event live: by iCalUID; an occurrence by `events.instances?originalStart=` from its recurrence_id. Never from Home Assistant's local copy.
3. Refuse invitations, events with any guest but Will, special event types, and a repeating event without an occurrence and a scope. Offer "This one" and "All" only; refuse a time change for all on a series with exceptions.
4. Write with `If-Match` and `sendUpdates=none` (`all` for a shared plan with Will, so his iCloud copy gets Google's update); one occurrence is a patch on the instance, deleting one is a patch to cancelled, all is a patch on the series (and its exceptions' text), deleting all is a delete. On 412, say so and re-read.
5. Do Google deletes through this path too, not Home Assistant's.
6. Whose: write the new copy with the same uid, compare, delete the old; on any failure keep exactly one.
7. Afterwards refresh the entity and the calendar copy; keep what Undo needs (old fields, tombstone id, old object text), and let an out-of-date Undo lose.
8. Repeats: patch `recurrence` in place (the uid stays); Never is an inclusive `UTC` `UNTIL` at the opened occurrence, with later changed occurrences cancelled first; a new rule replaces the `RRULE` line; refuse a new rule on a series with exceptions.
9. Shared plans: re-ask Will's calendar after the write and let the echo name his copy while it lags; Whose leaves a shared plan where it is.

No owner decision: Jenn's consent screen and the Cloud setup are as the switch-over approved; the only guest who is ever mailed is Will, as #104 decided ("sending its usual update email"); and the one open question, whether iCloud applies Google's update without Will acting, already has #104's decided fallback (option C) if step 20 says no.

## Gaps

- **Not run against Google.** Everything about Google comes from its reference pages and discovery document, or is an assumption listed in `fake_google.py`.
- Google's instance id form is relied on by `gcal_sync` but not documented by Google; the path uses `originalStart` and only splits the id to get the series id.
- What Google does to exceptions when a series' time or rule changes; whether it carries text changes to exceptions; whether deleting a series and restoring it brings exceptions back.
- Whether insert or import keeps a caller's iCalUID, which one makes the calendar the organizer, and whether a tombstone blocks reusing an iCalUID.
- Whether Google ever lists an exception before its series in a sync (lesson 1).
- Whether Google sends the calendar owner anything about her own API edits.
- How iCloud names and stores an object whose UID is `…@google.com` (step 12).
- Whether patching `recurrence` turns a one-off into a series on real Google, whether `recurrence: []` turns it back, and what Google does with exceptions after an `UNTIL` or a rule change (steps 14 to 16).
- **Whether iCloud applies Google's emailed update or cancellation to an accepted invitation without Will acting** (Apple documents only where invitations appear; community reports disagree; step 19 and 20). This decides #104's fallback.
- Whether an invitation reaches Will's iCloud copy under the same UID (step 18); what Google does when an attendee's copy is patched (never tried by the board).
- Whether restoring a deleted shared plan re-invites Will (step 20).
